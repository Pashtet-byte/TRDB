# Самостоятельная работа №3

**Тема:** Анализ планов выполнения запросов, аудит индексирования и оптимизация структур хранения данных в СУБД

**Вариант №13**

**СУБД:** PostgreSQL 16

---

## 1. Проблемная ситуация

**Формулировка варианта:** поиск по JSON-полю `metadata->>'device_id'` в таблице `devices` выполняется через полное сканирование таблицы.

**Задание:** написать DDL для создания индексной структуры по JSONB-полю.

**Исходная структура и запрос.** В задании структура таблицы не приведена, поэтому для воспроизведения принята типовая: данные об устройствах (датчики, терминалы, счётчики) хранятся в таблице с обычными столбцами и полуструктурированным столбцом `metadata` типа `JSONB`, в котором лежит идентификатор устройства. Для проверки таблица заполняется 1 000 000 строк.

```sql
CREATE TABLE devices (
    id            BIGSERIAL   PRIMARY KEY,
    serial_no     VARCHAR(30) NOT NULL,
    registered_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    metadata      JSONB       NOT NULL
);

INSERT INTO devices (serial_no, metadata)
SELECT 'SN-' || LPAD(g::text, 8, '0'),
       jsonb_build_object(
           'device_id', 'DEV-' || LPAD(g::text, 8, '0'),
           'model',     'M' || (g % 20),
           'firmware',  '1.' || (g % 10),
           'location',  jsonb_build_object('city',  (ARRAY['Москва', 'Казань', 'Самара'])[1 + g % 3],
                                           'floor', g % 5))
FROM generate_series(1, 1000000) g;

VACUUM ANALYZE devices;
```

**Проблемный запрос:**

```sql
SELECT id, serial_no
FROM devices
WHERE metadata ->> 'device_id' = 'DEV-00500000';
```

---

## 2. Диагностика и причина проблемы

### 2.1. План выполнения

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, serial_no
FROM devices
WHERE metadata ->> 'device_id' = 'DEV-00500000';
```

План до оптимизации (существенные строки):

```text
Seq Scan on devices (actual rows=1 loops=1)
  Filter: ((metadata ->> 'device_id'::text) = 'DEV-00500000'::text)
  Rows Removed by Filter: 999999
  Buffers: shared hit=14757 read=10243
Execution Time: 102.360 ms
```

Для одной нужной строки СУБД просмотрела всю таблицу: отбросила 999 999 строк и прочитала 25 000 страниц (≈ 195 МБ). Время растёт линейно с размером таблицы.

### 2.2. Причины

1. **Индекса по выражению нет.** B-Tree индекс хранит значения столбца или выражения в отсортированном виде. Условие `metadata ->> 'device_id' = ...` содержит вычисляемое выражение, а готовых значений `metadata ->> 'device_id'` ни в каком индексе нет, поэтому планировщик вынужден вычислять выражение для каждой строки.
2. **Индекс по самому столбцу `metadata` не помогает.** B-Tree по `JSONB`-столбцу сравнивает документы целиком, а не отдельные ключи. GIN-индекс по `metadata` (оператор-класс `jsonb_ops`) поддерживает операторы `@>`, `?`, `?|`, `?&`, `@?`, `@@`, но **не оператор `->>`**. Это проверено: после создания обычного `GIN (metadata)` запрос с `->>` остался `Seq Scan` (99,2 мс).
3. **Правило совпадения выражения.** Планировщик использует индекс по выражению только если выражение в `WHERE` совпадает с выражением индекса. Индекс по `(metadata ->> 'device_id')` не подойдёт для условия `metadata -> 'device_id' = '"..."'`, потому что `->` возвращает `jsonb`, а `->>` — `text`. Если в запросе применяется приведение типа (`(metadata ->> 'device_id')::int`), то и индекс нужно строить по выражению с тем же приведением.

---

## 3. Решение

### 3.1. Основное решение: B-Tree индекс по выражению

Запрос ищет **точное совпадение** по одному известному ключу — для этого лучше всего подходит B-Tree индекс по выражению `metadata ->> 'device_id'`.

```sql
-- Индекс по выражению. Дополнительные скобки вокруг выражения обязательны.
-- CONCURRENTLY: создание без блокировки записи в таблицу (важно для продуктивной БД;
-- команду нельзя выполнять внутри транзакции).
CREATE INDEX CONCURRENTLY idx_devices_meta_device_id
    ON devices ((metadata ->> 'device_id'));

-- Статистика по выражению собирается только при ANALYZE:
-- без неё планировщик оценивает селективность наугад.
ANALYZE devices;
```

Если по бизнес-правилам `device_id` уникален, вместо обычного создаётся уникальный индекс. Он ускоряет поиск так же и дополнительно запрещает дубли идентификатора:

```sql
-- Вариант для уникального идентификатора (взаимоисключающий с индексом выше)
-- CREATE UNIQUE INDEX CONCURRENTLY uq_devices_meta_device_id
--     ON devices ((metadata ->> 'device_id'));
```

Исходный запрос менять не нужно:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, serial_no
FROM devices
WHERE metadata ->> 'device_id' = 'DEV-00500000';
```

## 4. Ожидаемый и полученный результат

### 4.1. План после оптимизации

```text
Index Scan using idx_devices_meta_device_id on devices (actual rows=1 loops=1)
  Index Cond: ((metadata ->> 'device_id'::text) = 'DEV-00500000'::text)
  Buffers: shared hit=4
Execution Time: 0.057 ms
```

План изменился с `Seq Scan` на `Index Scan`: вместо фильтрации миллиона строк СУБД спускается по B-Tree до одного значения и читает одну страницу таблицы.
