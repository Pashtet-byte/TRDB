# Самостоятельная работа №4

**Вариант №13**

---

## Исходная схема и условие

Таблица `Tickets(ticket_id, flight_no, seat_no, passenger_id, aircraft_type)`.
Первичный ключ: `ticket_id`.
Бизнес-правила: номер рейса однозначно определяет тип самолёта (`flight_no -> aircraft_type`); на одном рейсе одно место может быть продано только один раз.

**Задание:** устранить транзитивную зависимость (3НФ) и добавить ограничение `UNIQUE(flight_no, seat_no)`.

Пример данных исходной таблицы:

| ticket_id | flight_no | seat_no | passenger_id | aircraft_type |
| --------- | --------- | ------- | ------------ | ------------- |
| 1         | SU100     | 12A     | 501          | Airbus A320   |
| 2         | SU100     | 12B     | 502          | Airbus A320   |
| 3         | SU200     | 7C      | 503          | Boeing 737    |

---

## 1. Функциональные зависимости

- `ticket_id -> flight_no, seat_no, passenger_id, aircraft_type` (первичный ключ);
- `flight_no -> aircraft_type` (из условия);
- `(flight_no, seat_no) -> ticket_id, passenger_id` (из условия: место на рейсе продаётся один раз, поэтому пара `(flight_no, seat_no)` — второй потенциальный ключ).

Потенциальные ключи таблицы: `ticket_id` и `(flight_no, seat_no)`.

---

## 2. Диагностика нарушения нормальной формы

- **1НФ:** соблюдена (все поля атомарны).
- **2НФ:** относительно первичного ключа `ticket_id` соблюдена, так как ключ простой. Но если учесть второй потенциальный ключ `(flight_no, seat_no)`, то неключевой атрибут `aircraft_type` зависит от его части (`flight_no`), то есть формально нарушение проявляется уже здесь.
- **3НФ: НАРУШЕНА.**
  _Причина:_ транзитивная зависимость `ticket_id -> flight_no -> aircraft_type`. Тип самолёта зависит не от билета, а от рейса, то есть от другого неключевого атрибута.
- **НФБК: НАРУШЕНА.**
  _Причина:_ в зависимости `flight_no -> aircraft_type` детерминант `flight_no` не является потенциальным ключом: на одном рейсе продаётся много билетов.

**Аномалии, к которым это приводит:**

1. **Аномалия вставки:** нельзя записать в базу рейс и тип его самолёта, пока не продан хотя бы один билет.
2. **Аномалия обновления:** при замене самолёта на рейсе SU100 тип нужно изменить во всех строках с этим рейсом (1, 2 и всех последующих); если пропустить хотя бы одну, у одного рейса окажется два разных типа самолёта.
3. **Аномалия удаления:** при возврате последнего билета на рейс SU200 пропадёт информация о том, что на нём летает Boeing 737.

---

## 3. Декомпозиция

Тип самолёта выносится в отдельную таблицу рейсов. Разложение выполняется без потерь: общий атрибут `flight_no` является ключом таблицы `Flights`, поэтому исходная таблица восстанавливается соединением по этому полю. Зависимость `flight_no -> aircraft_type` сохраняется.

1. `Flights(flight_no PK, aircraft_type)` — рейсы и тип самолёта.
2. `Tickets(ticket_id PK, flight_no FK, seat_no, passenger_id)` — билеты, `UNIQUE(flight_no, seat_no)`.

После декомпозиции все детерминанты зависимостей — потенциальные ключи, поэтому схема находится в 3НФ и в НФБК.

## 4. Реализация на SQL (PostgreSQL)

```sql
-- Рейсы: тип самолёта хранится один раз для каждого рейса
CREATE TABLE flights (
    flight_no     VARCHAR(10) PRIMARY KEY,
    aircraft_type VARCHAR(40) NOT NULL
);

-- Билеты
CREATE TABLE tickets (
    ticket_id    BIGSERIAL PRIMARY KEY,
    flight_no    VARCHAR(10) NOT NULL
        REFERENCES flights (flight_no) ON DELETE RESTRICT ON UPDATE CASCADE,
    seat_no      VARCHAR(4)  NOT NULL,
    passenger_id INT         NOT NULL,  -- ссылка на справочник пассажиров (вне рамок задания)
    -- Одно место на рейсе нельзя продать дважды
    CONSTRAINT uq_flight_seat UNIQUE (flight_no, seat_no)
);
```

Исходное представление данных (с типом самолёта в каждой строке) при необходимости получается запросом:

```sql
SELECT t.ticket_id, t.flight_no, t.seat_no, t.passenger_id, f.aircraft_type
FROM tickets t
JOIN flights f ON f.flight_no = t.flight_no;
```

## 5. Вывод

- **Целостность.** Тип самолёта хранится один раз, поэтому у рейса не может оказаться двух разных типов; замена самолёта выполняется изменением одной строки в `Flights`. Ограничение `UNIQUE(flight_no, seat_no)` на уровне СУБД исключает двойную продажу места, даже если приложение или два параллельных запроса пропустят эту проверку. Внешний ключ с `ON DELETE RESTRICT` не позволяет удалить рейс, на который проданы билеты. Информация о рейсе больше не зависит от наличия билетов: аномалии вставки и удаления устранены.
- **Безопасность.** Данные о рейсах и данные о пассажирах разделены по таблицам, поэтому права можно выдавать раздельно: диспетчерам и аналитикам — доступ к `Flights` без доступа к `Tickets`, где есть привязка к пассажирам (принцип минимальных привилегий).
- **Производительность.** Таблица `Tickets`, самая большая в схеме, уменьшается: строка `aircraft_type` больше не повторяется в каждом билете. Индекс, который создаётся для `UNIQUE(flight_no, seat_no)`, одновременно ускоряет проверку занятости места и выборку всех мест рейса. Платой за нормализацию становится соединение с небольшой таблицей `Flights` по первичному ключу, когда в запросе нужен тип самолёта; для такой таблицы оно дешёвое.
